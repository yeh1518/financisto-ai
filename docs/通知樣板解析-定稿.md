# 通知樣板解析（AI 產樣板）——定稿（2026-07-23）

> **接手本專案的 session 一律以繁體中文回應與產出。**
>
> 路線 B 擴想收斂結果（B0/B1/B2 比較後 Gary 拍板）：**B2 直達**——AI 只負責「產樣板」這
> 一次性工作，執行期回歸原生通知樣板機制（零 API 費、離線、隱私：LLM 只在生成那刻看樣本）。
> 不做 app 白名單（Gary 明示反感 app 選擇器；樣板以通知標題為鍵，過濾天然免費——LINE 裡
> 的銀行官方帳號標題就是鍵）。不做 B1 批次中繼介面（批次確認＝blotter 篩 UR，原生已有）。

## 使用者流程

```
AI 設定 → 「通知樣板解析」
  → 通知列表（新：讀持久化日誌，非只讀 NotificationCache）
  → 選一則
  → LLM 生成樣板（標題鍵/樣板文字/綁定帳戶/綁定分類）
  → 程式自動驗證（原生引擎回測 + 金額變異測試）
  → 預填進原生樣板編輯器（SmsTemplateActivity）
  → Gary 過目、按存 → 之後由原生機制全自動記帳
```

## 已拍板的決定

| 決定 | 內容 |
|---|---|
| 通知日誌 | **v1 就做持久化**：滾動日誌，近 7 天、只留內文含數字的、上限 ~100 則。解決 NotificationCache 只存「未滑掉通知」的撲空問題；也是未來「樣板失效偵測」的基礎 |
| 生成落點 | **預填原生樣板編輯器**讓 Gary 過目按存（不自動存） |
| 入口 | AI 設定頁（AiSettingsActivity）新增項目，不動實體選單既有入口 |

## LLM 生成設計

- **輸入**：選中通知（標題+內文）＋佔位符規格（`{{p}}` 金額必填、`{{a}}` 末四碼、`{{e}}` 商家、
  `{{*}}` 跳過…見 `SmsTransactionProcessor.Placeholder`）＋帳戶清單（含 hint/卡號）＋分類清單
  （重用 `EntityContextBuilder`）。
- **輸出**（strict schema，同解析鏈老套路）：`標題鍵、樣板文字、account_id、category_id、信心值`。
- **確定性驗證（不靠 LLM 自覺）**：
  1. 原生引擎回測：`SmsTransactionProcessor.findTemplateMatches(樣板, 樣本內文)` 必須比中，
     且抽出金額 == 樣本金額（LLM 一併回報樣本金額供比對）。失敗帶錯誤訊息自動重試一次。
  2. 金額變異測試：把樣本金額換不同位數（65 → 1,234.00）再回測，仍須比中——防過擬合
     （如把金額寫死成固定位數）。
- 樣本含卡號末四碼時**優先用 `{{a}}`**：原生機制以末四碼對帳戶卡號欄，一條樣板通吃多卡。
- 同一標題可存多條樣板（同銀行的消費/繳款/行銷各一條或不設）：原生查找本來就回 list、
  不比中就不動作，安全。

## 通知日誌（新元件）

- 新表（rolling）：`title / body / package / 時間戳`；寫入點＝`NotificationListener.processNotification`
  （前濾：內文含數字才記，行銷雜訊大多擋掉）；自動清理：>7 天或超額刪最舊。
- 列表 UI 複用 `NotificationListActivity` 的形（改資料來源＋點擊行為：AI 設定入口進來＝
  「選則生成」；實體選單原入口維持「複製到剪貼簿」不動）。
- 隱私：日誌純本地，隨 app 資料存在；**不進備份檔**（不是帳務資料）。
- 每筆的時間戳＝通知的 `postTime`，不是寫檔當下。`onListenerConnected` 會把通知欄裡還掛著
  的舊通知整批重掃，用當下時間會把它們全壓成「app 啟動那一刻」；而這個時間會被當成交易
  時間用（見下），錯不起。

## 排除清單

挑選模式的列表要在一堆限時動態、行銷推播、同步狀態裡翻，而日誌只有 ~100 筆額度——雜訊會
把真正的銀行通知擠掉。所以清單**兩邊都套**：日誌不記、列表不顯示（顯示這層另外過濾，是為了
「改掉規則被擋的東西就回來」）。

存成一整段純文字（`NotificationFilter`，一行一條規則），不是結構化清單：要的是打開來看一眼、
順手改幾行，也要能從對話裡貼進貼出。兩種行：

| 行 | 意思 |
|---|---|
| `app:com.instagram.android  # Instagram` | 排掉整個 app。後面接的字是給人看的註記（套件名不含空白也不含 `#`） |
| 其餘 | 關鍵字，對標題與內文做忽略大小寫的子字串比對 |
| `#` 開頭 | 註解 |

不做 regex（寫錯一個字元就整條失效的東西不值得），也不做 app 選擇器——排除 app 的入口是
**某則通知的動作選單裡的一鍵排除**，不必先知道套件名是什麼。關鍵字擋不乾淨的東西
（IG 限時動態的「和另外 2 人」照樣有數字，過不了「含數字」那關）才是額度的主要殺手，
整個 app 排掉才守得住。

顯示 app 名稱要靠 manifest `<queries>` 宣告 MAIN/LAUNCHER：targetSdk 30+ 的 package
visibility 下，對任意套件查 `getApplicationInfo` 會 `NameNotFoundException`，notification
listener 沒有豁免。刻意不用 `QUERY_ALL_PACKAGES`（那是為了列舉整台手機）。查不到就顯示
套件名——它同時也是 `app:` 規則要寫的值，不是廢資訊。

## 從列表記帳時的交易時間

日誌留 7 天，所以從列表點下去的三條路（產樣板後回套／套現有樣板／直接解析）都可能在處理
好幾天前的通知。交易時間的優先序：

1. 樣板抽到的 `{{g}}` 時間戳——銀行自己給的，最準
2. 通知的 `postTime`
3. 記帳的當下

背景自動入帳不走這套（收到就記，當下 ≈ 通知時間），所以 `SmsTransactionProcessor.process`
的無時間版本維持原樣。「直接解析」那條走 AI 管線，模型從內文解析出日期時以那個為準，
沒解析出來才退到 `postTime`（`AiInputActivity.BASE_TIME_EXTRA`）。

## v2 掛鉤（先不做，設計時留縫）

- **樣板失效偵測**：日誌中「標題吃得到樣板、內文比不中」的通知打徽章「樣板沒吃到」，
  點一下重生成——「常常要維護」變一鍵維護。
- 多樣本強化：生成時自動撈日誌中同標題的其他樣本一起餵，泛化更穩。

## 未來 TODO：樣板投報率問題（2026-07-29 擴想後暫緩）

**現況**：機制本身正常，是「值不值得設」的問題——設一次樣板的投報率不夠高：

1. **涵蓋率天生受限**：多數消費通知來自 LINE，內容只有「有一筆消費」而無金額/商家明細，
   規則再好也抽不出東西；真正能用的只有銀行/信用卡自家 app 的通知。
2. **樣板只能設到最寬**：同一張卡什麼都刷，樣板抓得到卡別與金額，抓不到分類——為了通吃
   只能放棄分類。於是通知裡的「XX 消費 / 商家名」這條**現成的分類線索被整段浪費**，
   而樣板本身沒有判斷力可以用它。
3. 產樣板時**沒有地方表達「這個樣板要寬還是窄」**，只能任 LLM 自行拿捏。

**收斂到的方向**（想清楚了但先不做）：

- **寬窄是假議題，真正的維度是欄位**。樣板產出從「一條 regex」改成**欄位 → 捕捉群組的
  mapping**：金額（變動、必抓）、帳戶（末四碼固定對應）、日期、**商家（變動、捕捉成自由
  文字）**、分類（不由 regex 決定，標記為「交給 AI」）。使用者看得懂也改得動，模型也拿到
  明確指令。這是主要手術點（`TemplateGenerator` 的 schema）。
- **捕捉後補完**：樣板負責捕捉確定欄位，捕捉到之後**把商家那段自由文字送 LLM 補完分類**，
  是否補完做成**每條樣板自己的設定**（固定用途的通知就純規則、零成本；信用卡才開補完）。
  不做「手動挑一則通知直送 LLM」的第二入口——那會是永遠不會去點的路。
- **商家 → 分類學習表**：命中直接用、不打 API，沒見過才問一次然後寫回；手動改過的永遠優先。
  個人消費商家重複率高，很快收斂，等於 LLM 只在遇到新商家時付費一次。**與掃圖記帳共用
  同一張表與同一個補完器**（確定欄位用規則、模糊欄位交給 LLM、重複的用查表）。
- **re-apply**：產完樣板立刻回套那則樣本並補記該筆。既是樣板的即時驗證（套不出＝樣板有
  問題，當場退回重產，而不是下個月才發現），也解決「拿來產樣板的那一則自己漏記」。
- **去重**（做上述任一項都必須同時做）：樣板自動記、re-apply、通知重複 post 會互相撞。
  通知日誌要加 consumed 標記（package + postTime + 內文 hash）。

**再啟動的條件**：掃圖記帳把「補完器 + 商家分類學習表」做出來之後——那時這裡只剩
「樣板改欄位 mapping + 呼叫補完器」，成本降一大截，投報率才翻正。
