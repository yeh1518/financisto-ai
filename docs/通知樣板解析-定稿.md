## 使用者流程

```
AI 設定 → 「通知樣板解析」
  → 通知列表（新：讀持久化日誌，非只讀 NotificationCache）
  → 選一則
  → LLM 生成樣板（標題鍵/樣板文字/綁定帳戶/綁定分類）
  → 程式自動驗證（原生引擎回測 + 金額變異測試）
  → 預填進原生樣板編輯器（SmsTemplateActivity）
  → Gary 過目、按存 → 之後由原生機制全自動記帳
```

## 已拍板的決定

| 決定 | 內容 |
|---|---|
| 通知日誌 | **v1 就做持久化**：滾動日誌，近 7 天、只留內文含數字的、上限 ~100 則。解決 NotificationCache 只存「未滑掉通知」的撲空問題；也是未來「樣板失效偵測」的基礎 |
| 生成落點 | **預填原生樣板編輯器**讓 Gary 過目按存（不自動存） |
| 入口 | AI 設定頁（AiSettingsActivity）新增項目，不動實體選單既有入口 |

## LLM 生成設計

- **輸入**：選中通知（標題+內文）＋佔位符規格（`{{p}}` 金額必填、`{{a}}` 末四碼、`{{e}}` 商家、
  `{{*}}` 跳過…見 `SmsTransactionProcessor.Placeholder`）＋帳戶清單（含 hint/卡號）＋分類清單
  （重用 `EntityContextBuilder`）。
- **輸出**（strict schema，同解析鏈老套路）：`標題鍵、樣板文字、account_id、category_id、信心值`。
- **確定性驗證（不靠 LLM 自覺）**：
  1. 原生引擎回測：`SmsTransactionProcessor.findTemplateMatches(樣板, 樣本內文)` 必須比中，
     且抽出金額 == 樣本金額（LLM 一併回報樣本金額供比對）。失敗帶錯誤訊息自動重試一次。
  2. 金額變異測試：把樣本金額換不同位數（65 → 1,234.00）再回測，仍須比中——防過擬合
     （如把金額寫死成固定位數）。
- 樣本含卡號末四碼時**優先用 `{{a}}`**：原生機制以末四碼對帳戶卡號欄，一條樣板通吃多卡。
- 同一標題可存多條樣板（同銀行的消費/繳款/行銷各一條或不設）：原生查找本來就回 list、
  不比中就不動作，安全。

## 通知日誌（新元件）

- 新表（rolling）：`title / body / package / 時間戳`；寫入點＝`NotificationListener.processNotification`
  （前濾：內文含數字才記，行銷雜訊大多擋掉）；自動清理：>7 天或超額刪最舊。
- 列表 UI 複用 `NotificationListActivity` 的形（改資料來源＋點擊行為：AI 設定入口進來＝
  「選則生成」；實體選單原入口維持「複製到剪貼簿」不動）。
- 隱私：日誌純本地，隨 app 資料存在；**不進備份檔**（不是帳務資料）。

## v2 掛鉤（先不做，設計時留縫）

- **樣板失效偵測**：日誌中「標題吃得到樣板、內文比不中」的通知打徽章「樣板沒吃到」，
  點一下重生成——「常常要維護」變一鍵維護。
- 多樣本強化：生成時自動撈日誌中同標題的其他樣本一起餵，泛化更穩。
