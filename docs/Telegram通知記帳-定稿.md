# Telegram 通知記帳（Claudy 圖片記帳）——定稿（2026-08-03）

> **接手本專案的 session 一律以繁體中文回應與產出。**
>
> 一句話：**app 端零改動**。把圖片記帳的「腦」外包給 Telegram bot（Claudy），
> 由它把辨識結果發成**格式固定的 Telegram 訊息**，落到手機通知欄，再由 app
> **既有的通知樣板引擎**把它記成交易。掃圖記帳的能力用外掛的方式先拿到手。

```
手機貼圖給 Claudy ＋ 關鍵字「記帳」（＋補充資訊）
  → Claudy（VM poller → AMD2024 claude -p，vision 讀圖）辨識出 N 筆
  → 回發 N 則格式固定的 Telegram 訊息（每則間隔數秒）
  → 手機通知欄出現 N 則通知，標題＝Claudy
  → Financisto 通知樣板引擎逐則比中 → 自動記帳 N 筆
```

## 為什麼可行（引擎的三個關鍵事實）

| 事實 | 出處 | 影響 |
|---|---|---|
| 樣板的鍵＝**通知標題**，且是 SQL `LIKE` **pattern** 比對（`where ? LIKE title`）| `DatabaseAdapter.getSmsTemplatesByNumber` | 標題填 `Claudy%` 就吃得到 Telegram 可能加的後綴 |
| 比對用的內文＝`標題 + " " + 通知文字` | `NotificationListener.extractNotification` | 樣板文字只要描述訊息本體即可 |
| 一則通知**只產一筆**交易，且**只有第一條比中的樣板生效** | `SmsTransactionProcessor.createTransactionBySms` | 三筆帳＝三則獨立訊息；多樣板靠關鍵字互斥 |

去重守則：同一則通知的 body 與上一次相同就跳過（`NotificationListener` L129）。
→ **每則訊息的內文必須互不相同**，用序號欄位保證。

## 通知格式（一則＝一筆）

```
🧾記帳｜支出｜250｜中信信用卡｜全家超商 晚餐便當｜1785761364401｜1/3
```

`🧾記帳｜方向｜金額｜帳戶｜備註｜時間戳｜序號`，全形 `｜` 分隔、**分隔符兩側不留空白**。

| 欄位 | 佔位符 | 規則 |
|---|---|---|
| 方向 | —（樣板文字寫死）| `支出` / `收入`，決定用哪條樣板（正負號來自樣板的 `is_income`）|
| 金額 | `{{p}}` | **一律正數**、**不要千分位**、小數點用 `.` |
| 帳戶 | `{{c}}` | Financisto **帳戶名稱原文**；比不到會 fallback 到樣板預設帳戶 |
| 備註 | `{{t}}` | 商家、品項、分類線索都寫這裡；可空、可含空白 |
| 時間戳 | `{{g}}` | epoch **毫秒**；引擎直接寫進 `dateTime`，故可補記過去日期 |
| 序號 | —（落在比對範圍外）| `1/3`，只為了讓同批訊息內文互異、不被去重擋掉 |

**沒有商家欄（`{{e}}`）是刻意的**（2026-08-03）：`{{e}}` 唯一的作用是寫進**受款人**，
而帳本只有 6 個受款人＝這欄沒在用；留著會讓每筆自動記帳長出一個沒主動建過的受款人，
為了一條外掛路線改變帳本的形狀。商家併進備註，順帶甩掉 `{{e}}` 的「不可含空白」限制。

## 樣板設定（app 端，兩條）

標題（兩條都）：`Claudy%`　分類：**無分類**　帳戶：**沒有帳戶**（不要設 fallback，理由見下）

支出（`is_income` 不勾）：
```
🧾記帳｜支出｜{{p}}｜{{c}}｜{{t}}｜{{g}}｜
```

收入（`is_income` 勾）：
```
🧾記帳｜收入｜{{p}}｜{{c}}｜{{t}}｜{{g}}｜
```

轉帳（`is_income` 不勾；多一格目標帳戶）：
```
🧾記帳｜轉帳｜{{p}}｜{{c}}｜{{x}}｜{{t}}｜{{g}}｜
```

- 尾端那個 `｜` 是 `{{g}}` 的右界，**不能省**。
- **為什麼收入支出要兩條**：方向不是引擎讀得到的文字欄位，而是**樣板上的一個布林**
  （`SmsTemplate.isIncome`），只在算正負號時用到：
  `fromAmount = (isIncome ? 1 : -1) * abs(price)`，而且引擎硬性要求 `price > 0`。
  所以「這筆是收是支」只能由**哪一條樣板比中**來表達——一條樣板＝一個固定方向，
  兩個方向就要兩條。樣板文字裡的「支出」／「收入」字面讓兩條互斥，每則訊息只會中一條。
- **分類留空是刻意的**：見下節——分類走事後批次補，不從通知帶。
- **帳戶留「沒有帳戶」、不要設 fallback**（2026-08-03 查清失敗路徑後改的建議）：
  帳戶名比不到時 `accountId` 停在 -1 → `price > 0 && accountId > 0` 不成立 → **不建交易**，
  改走 `db.log()`。而 Financisto 的 `db.log()` 不是寫 log 檔，是**在第一個有效帳戶插一筆
  0 元交易，備註帶完整錯誤訊息與通知原文**（`DatabaseAdapter` L2188）。
  ＝**錯誤留下的是證據，不是髒資料**：餘額不受影響，原文還在，可以照著手補。
  設 fallback 則相反——錯的金額真的落進一個真帳戶、算進餘額，且長得跟正常交易一樣，
  只有帳戶欄不對。代價只有那筆 0 元殘骸要自己刪，而它出現本身就是「有一筆沒進來」的告警。

## 轉帳（2026-08-03 加入，需搭配一行引擎修正）

轉帳訊息多一格目標帳戶，共七欄：

```
🧾記帳｜轉帳｜5000｜中信帳戶總覽｜身上現金｜ATM 提款｜1785769151816｜1/2
```

`{{x}}` 走 `getEntityIdByTitle(Account)` 找目標帳戶，`is_income=false` 時
`fromAmount = -金額`、`toAmount = +金額`——錢從 `{{c}}` 出、進 `{{x}}`。

### 為什麼要改引擎：`{{x}}` 原本對中文帳本完全無效

`TRANSFER_TO_ACCOUNT_NAME` 原本用 `(\w+?)`，而 **Java 的 `\w` 是 ASCII-only**
（未開 `UNICODE_CHARACTER_CLASS`）。JDK 21 實測：

| 帳戶名 | `(\w+?)` | `(\S+?)` |
|---|---|---|
| `身上現金` | ✗ 不比中 | ✓ |
| `LineBank` | ✓ | ✓ |
| `Richart帳戶` | ✗ 不比中 | ✓ |
| `(存款)` | ✗ 不比中 | ✓ |

帳本裡除 `LineBank` 外全是中文 → **這個佔位符等於不存在**。這是上游的不一致：
`{{c}}`／`{{e}}`／`{{r}}` 都用 `(\S+?)`，只有 `{{x}}` 用 `(\w+?)`。改成 `(\S+?)` 對齊；
`\S` 是 `\w` 的超集，既有 ASCII 樣板行為不變。

### ⚠️ 轉帳的失敗模式比支出危險

目標帳戶名比不到時 `transferToAccountId` 停在 0 → **不會不記，而是記成一筆單純支出**
（`if (transferToAccountId != 0)` 不成立，`toAccountId` 沒設）。錢從來源帳戶出去、
沒有進到任何地方＝**淨值平白減少**，而且它長得像一筆正常消費。

對照 `{{c}}` 比不到是「整筆不記＋0 元殘骸」——安全得多。這個不對稱要記著。
兩種收斂法：

- **樣板的「轉帳對象」留「不轉帳」**（現行）：失敗＝變成支出，靠備註看得出本意是轉帳。
- **指定一個暫掛帳戶當轉帳對象**：失敗＝轉進暫掛帳戶，**淨值不受影響**、位置錯而已，
  但要為此在帳本裡多一個帳戶。轉帳的本質是淨值中性，這個選項在正確性上較好。

## 分類：不從通知走，事後批次補（2026-08-03 拍板）

**通知樣板這條管子沒有分類這個孔。** 佔位符只有金額 / 卡號 / 帳戶名 / 轉帳對象 /
幣別 / 受款人 / 專案 / 備註 / 時間戳 / 跳過（`Placeholder` enum），**沒有分類**。
交易的分類只有兩個來源：樣板上綁死的那一個，或受款人身上記著的上一次分類。

> **最容易想混的地方**：這不是「Claudy 不知道我的分類」。腦跑在 AMD2024、帳本備份
> 就在那台，它要讀 78 個分類名隨時讀得到。**是管路沒有這個孔，不是它不知道。**
> 對照 app 內的 AI 記帳為什麼做得到——那條路根本沒走樣板：`EntityContextBuilder`
> 把分類樹攤平成全路徑餵進 prompt，模型回 `category_id` 直接寫進交易。
> 差別是「LLM 直接產結構化欄位」vs「regex 從文字裡撈欄位」，不是誰比較聰明。

順帶一提，受款人與專案都有「照名字找不到就建一個」（`findOrInsertEntityByTitle`），
分類沒有——分類是樹（`left`/`right` 巢狀集合），憑一個名字決定不了它該長在樹的哪裡。

### 評估過的三條路

| 路 | 做法 | 代價 |
|---|---|---|
| A 一分類一樣板 | 加一格分類欄、分類詞是樣板字面、分類綁在樣板上 | 手設十幾條＋兜底樣板；⚠️ 查找是 `order by sort_order, length(template) desc`，兜底含 `{{*}}`（5 字元）會排到具體分類（如 `飲食` 2 字元）前面**把訊息全吃掉**，必須拖曳排序壓到最後 |
| B 受款人帶分類 | `{{e}}` → `payee.lastCategoryId`（存交易時由 `updateLastUsed` 回寫）| 機制成立但**帳本只有 6 個受款人、3 個沒分類＝這欄根本沒在用**；等於從零建一張商家表，每個新商家要先錯一次 |
| **C 不從通知走分類** ✅ | 分類留空，事後在 blotter 篩出來批次補 | 多一道人工，但**零設定、零新制度、帳本形狀不變** |

**選 C。** 分類是 78 個、是記帳的核心，值得當下看一眼；受款人只有 6 個、是沒在用的欄位，
不該拿它承載分類。A 的十幾條樣板則是為了省一道批次補分類而長出一套要維護的制度，
投報率跟被擱置的〈通知樣板解析〉未來 TODO 是同一種——**先不建制度**。

這也回到七月底那份定稿早就寫下的收斂：「分類不由 regex 決定，標記為交給 AI」。

## 帳戶清單為什麼改成「每次現查」（2026-08-03）

引擎端查帳戶是 `getEntityIdByTitle` → 一句 `WHERE title = ?` 的**完全相等**比對
（`MyEntityManager` L591）：沒有模糊比對、沒有 LIKE、沒有 trim。所以 `{{c}}`／`{{x}}`
填的字串必須是**當下帳本裡的原文**，判斷力全在 Claudy 那一端。

原本給她的是一份靜態清單（從備份匯出的 34 個帳戶）。問題是**它是唯一一個會隨時間
自己壞掉的環節**——改帳戶名或新增帳戶時清單不會跟著動，而失敗是靜默的
（來源帳戶錯＝整筆不記；目標帳戶錯＝變成一筆支出、淨值減少）。改成每次記帳前從
最新的每日帳本備份現解，成本是一次 shell、不燒 API。

### 這個決定不直覺，脈絡值得留（Gary 2026-08-03）

> 「這多少有點利用 AI 的 overpower 跟便利性來處理小事情，沒那麼直覺。」

確實。人類做這件事的自然解法是「久久校正一次清單」——因為對人來說，每次記帳前
重跑一次查詢是明顯的浪費。**但『久久一次』正是最容易飄移的維護點**：它沒有觸發器、
沒有人會記得、而且壞掉的時候不會叫。於是「省下每次的小成本」換來的是「一個必然
會腐化的約定」。

在 LLM 這端，那個「每次」的成本趨近於零（一次 shell，不燒 API、不佔思考），
於是**人類世界的成本結構被翻轉了**：對人來說貴的（每次重查）變便宜，對人來說便宜的
（記得定期校正）反而還是貴——因為那個成本從來不是執行，是記得。

所以判準不是「這件事大不大」，而是**「這個環節會不會隨時間自己壞掉、壞了會不會叫」**。
會壞又不會叫的，就把它從『約定』改成『每次現查』，即使看起來殺雞用牛刀。
這條路上其他環節（格式、樣板、佔位符語義）都是靜態正確的，唯獨帳戶清單不是——
所以只有它值得這樣處理，不是全部都該這樣。

## Claudy 端

腦＝AMD2024 的 `claude -p`（cwd `myinfra`），圖片路徑已通（VM 下載 → scp → Read vision）。
規格住 `myinfra/telegram-control/記帳格式.md`（含帳本快照＝個人資料，Syncthing-only、不進 git），
`claudy-learnings.md` 留一行指標讓每次開場讀得到。帳戶清單在那份文件裡是**理解用的快照**，
實際填欄位走上一節的現查指令。

**發送方式**：Claudy 逐筆自行呼叫 Telegram `sendMessage`（經 VM）、每則間隔數秒，
而不是把三筆塞進同一則回覆——poller 的一次回覆＝一則訊息＝一則通知＝最多一筆帳。

## 字面實測（2026-08-03，已通過）

Telegram 實際塞進通知的內容：

```
title = Claudy
body  = Claudy 🧾記帳｜收入｜32000｜中信帳戶總覽｜測試商家丙｜格式測試 3｜1785761364401｜3/3
```

標題乾淨、無「(3)」之類後綴；body 就是 `title + " " + 內文`。**與設計一致。**

**連發三則不會被併掉**：三則測試訊息在通知日誌裡是**三筆獨立記錄**。日誌的寫入點
就在 `processNotification`——與樣板比對是同一個進入點，所以「三則都進日誌」等於
「三則的 body 都各自送進過比對器」，且序號讓 body 互異、沒有被去重守則擋掉。
這是這條路最大的未知數（Telegram 併訊息會讓中間幾筆靜默消失），已排除。

引擎的 `findTemplateMatches` 邏輯原樣重跑（escape → 佔位符換 regex → `find`），五個案例全過：
正常支出／收入、小數金額、括號帳戶名 `(存款)`、空備註、備註含空白甚至含 `｜`——
切分都正確；收入樣板不會吃到支出訊息（跨樣板互斥成立）。

## 操作上的兩個坑（實測踩到）

- **Telegram 停在 Claudy 對話畫面時系統不發通知** → 引擎看不到 → 整批不記帳。
  而貼圖記帳的情境剛好就是「人在對話裡」。**貼完圖要退出對話**，讓訊息以通知形式落下。
- **listener 被系統解綁**（權限顯示還在但收不到）：先開一次「通知列表」觸發自癒
  （`NotificationListener.requestRebindIfGranted`），不一定要去關開權限。

兩者都會造成**靜默漏記**——你以為記了。故收尾動作是：Claudy 發完後回報「已送出 N 筆」，
你在 blotter 對數量。漏記要看得出來，不能靠感覺。

## 與既有兩條路線的關係

- [[通知樣板解析-定稿]]：本方案**用的就是它的執行期機制**，只是訊息來源從銀行 app
  換成自己的 bot——格式由我們自己定，於是它列的三個投報率痛點（涵蓋率、
  樣板抓不到分類、寬窄無法表達）在這裡天然不存在。
- [[掃圖記帳-定稿]]：本方案是它的**外掛先行版**——不進 app、不寫 code、直接拿到
  「拍圖就記帳」。差別在（a）走雲端 vision 而非本機 QR+OCR，（b）確認方式是
  事後在 blotter 篩 UR/PN 而非當場預填交易頁。app 內版本仍照原定稿走。
