# Telegram 通知記帳（Claudy 圖片記帳）——定稿（2026-08-03）

> **接手本專案的 session 一律以繁體中文回應與產出。**
>
> 一句話：**app 端零改動**。把圖片記帳的「腦」外包給 Telegram bot（Claudy），
> 由它把辨識結果發成**格式固定的 Telegram 訊息**，落到手機通知欄，再由 app
> **既有的通知樣板引擎**把它記成交易。掃圖記帳的能力用外掛的方式先拿到手。

```
手機貼圖給 Claudy ＋ 關鍵字「記帳」（＋補充資訊）
  → Claudy（VM poller → AMD2024 claude -p，vision 讀圖）辨識出 N 筆
  → 回發 N 則格式固定的 Telegram 訊息（每則間隔數秒）
  → 手機通知欄出現 N 則通知，標題＝Claudy
  → Financisto 通知樣板引擎逐則比中 → 自動記帳 N 筆
```

## 為什麼可行（引擎的三個關鍵事實）

| 事實 | 出處 | 影響 |
|---|---|---|
| 樣板的鍵＝**通知標題**，且是 SQL `LIKE` **pattern** 比對（`where ? LIKE title`）| `DatabaseAdapter.getSmsTemplatesByNumber` | 標題填 `Claudy%` 就吃得到 Telegram 可能加的後綴 |
| 比對用的內文＝`標題 + " " + 通知文字` | `NotificationListener.extractNotification` | 樣板文字只要描述訊息本體即可 |
| 一則通知**只產一筆**交易，且**只有第一條比中的樣板生效** | `SmsTransactionProcessor.createTransactionBySms` | 三筆帳＝三則獨立訊息；多樣板靠關鍵字互斥 |

去重守則：同一則通知的 body 與上一次相同就跳過（`NotificationListener` L129）。
→ **每則訊息的內文必須互不相同**，用序號欄位保證。

## 通知格式（一則＝一筆）

```
🧾記帳｜支出｜250｜中國信託｜全家超商｜晚餐便當｜1754204400000｜1/3
```

`🧾記帳｜方向｜金額｜帳戶｜商家｜備註｜時間戳｜序號`，全形 `｜` 分隔、**分隔符兩側不留空白**。

| 欄位 | 佔位符 | 規則 |
|---|---|---|
| 方向 | —（樣板文字寫死）| `支出` / `收入`，決定用哪條樣板（正負號來自樣板的 `is_income`）|
| 金額 | `{{p}}` | **一律正數**、**不要千分位**、小數點用 `.` |
| 帳戶 | `{{c}}` | Financisto **帳戶名稱原文**；比不到會 fallback 到樣板預設帳戶 |
| 商家 | `{{e}}` | **不可含空白**（引擎用 `\S+?`）；沒有就填固定詞（如 `未知`），不可空 |
| 備註 | `{{t}}` | 可空、可含空白 |
| 時間戳 | `{{g}}` | epoch **毫秒**；引擎直接寫進 `dateTime`，故可補記過去日期 |
| 序號 | —（落在比對範圍外）| `1/3`，只為了讓同批訊息內文互異、不被去重擋掉 |

## 樣板設定（app 端，兩條）

標題（兩條都）：`Claudy%`　分類：**留空**　預設帳戶：指到「待分類」性質的帳戶

支出（`is_income` 不勾）：
```
🧾記帳｜支出｜{{p}}｜{{c}}｜{{e}}｜{{t}}｜{{g}}｜
```

收入（`is_income` 勾）：
```
🧾記帳｜收入｜{{p}}｜{{c}}｜{{e}}｜{{t}}｜{{g}}｜
```

- 尾端那個 `｜` 是 `{{g}}` 的右界，**不能省**。
- **分類留空是刻意的**：`SmsTransactionProcessor` L234 一旦樣板有分類就會覆蓋掉商家帶來的分類。
- **預設帳戶不要指到常用帳戶**：帳戶名打錯時會無聲落到它（L167）。指到一個一眼看得出不對的帳戶，錯誤才會浮上來。

## 分類怎麼來：跟著商家走

引擎沒有「從文字讀分類」的能力。但 `{{e}}` 商家會走
`findOrInsertEntityByTitle(Payee)` → 套用 `payee.lastCategoryId`（L194-204）。
＝**同一個商家你手改一次分類，之後自動帶**。零設定的自學表，也正好是
[[掃圖記帳-定稿]] 裡「先蒐證、不建制度」想觀察的那份資料的真人版。

## 明確做不到（不要試）

| 項目 | 原因 | 現行處置 |
|---|---|---|
| **轉帳** | `{{x}}` 用 `\w+?`，比不中中文帳戶名 | 拆成一支一收兩則；或未來一條樣板固定一組帳戶 |
| **外幣** | `{{f}}` 命中且與帳戶幣別不同時，`fromAmount` 留 0（L216-228）| 格式**故意不含幣別**；外幣原始金額寫進備註 |
| **一筆拆多分類** | 引擎一則通知一筆 | Claudy 直接拆成多則（本來就是多則） |
| **分類直接指定** | 引擎無此欄位 | 靠商家自學（見上） |

## Claudy 端

腦＝AMD2024 的 `claude -p`（cwd `myinfra`），圖片路徑已通（VM 下載 → scp → Read vision）。
規格與帳戶清單住 `myinfra/telegram-control/記帳格式.md`（含個人資料，Syncthing-only、不進 git），
`claudy-learnings.md` 留一行指標讓每次開場讀得到。

**發送方式**：Claudy 逐筆自行呼叫 Telegram `sendMessage`（經 VM）、每則間隔數秒，
而不是把三筆塞進同一則回覆——poller 的一次回覆＝一則訊息＝一則通知＝最多一筆帳。

## 字面實測（2026-08-03，已通過）

Telegram 實際塞進通知的內容：

```
title = Claudy
body  = Claudy 🧾記帳｜收入｜32000｜中信帳戶總覽｜測試商家丙｜格式測試 3｜1785761364401｜3/3
```

標題乾淨、無「(3)」之類後綴；body 就是 `title + " " + 內文`。**與設計一致。**

**連發三則不會被併掉**：三則測試訊息在通知日誌裡是**三筆獨立記錄**。日誌的寫入點
就在 `processNotification`——與樣板比對是同一個進入點，所以「三則都進日誌」等於
「三則的 body 都各自送進過比對器」，且序號讓 body 互異、沒有被去重守則擋掉。
這是這條路最大的未知數（Telegram 併訊息會讓中間幾筆靜默消失），已排除。

引擎的 `findTemplateMatches` 邏輯原樣重跑（escape → 佔位符換 regex → `find`），五個案例全過：
正常支出／收入、小數金額、括號帳戶名 `(存款)`、空備註、備註含空白甚至含 `｜`——
切分都正確；收入樣板不會吃到支出訊息（跨樣板互斥成立）。

## 操作上的兩個坑（實測踩到）

- **Telegram 停在 Claudy 對話畫面時系統不發通知** → 引擎看不到 → 整批不記帳。
  而貼圖記帳的情境剛好就是「人在對話裡」。**貼完圖要退出對話**，讓訊息以通知形式落下。
- **listener 被系統解綁**（權限顯示還在但收不到）：先開一次「通知列表」觸發自癒
  （`NotificationListener.requestRebindIfGranted`），不一定要去關開權限。

兩者都會造成**靜默漏記**——你以為記了。故收尾動作是：Claudy 發完後回報「已送出 N 筆」，
你在 blotter 對數量。漏記要看得出來，不能靠感覺。

## 設定與後續驗證

1. 樣板列表 → 新增兩條（支出／收入），照上面的樣板文字。標題 `Claudy%`、分類留空。
2. 叫 Claudy 發一批測試，確認落帳筆數、帳戶／商家／日期都對。
3. 落帳狀態由設定的「簡訊交易狀態」決定（預設 `PN`）——留在未核銷狀態才方便在
   blotter 篩出來逐筆過目。

> 另一個入口差異（會踩）：**AI 記帳底排「通知解析」＝挑選模式**，點一則跳三動作選單；
> **樣板列表 → 選單 →「通知列表」＝一般模式**，點一則才是複製到剪貼簿。
